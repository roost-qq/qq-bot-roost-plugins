# 数据迁移与回退

适用版本：`0.3.0`／`0.3.1`，升级基线为用户已验收的 `0.2.0`。本文件描述操作步骤，不授权修改宿主、其他插件或生产安装。

`0.3.0 → 0.3.1` 仅修正状态与页面行为，不增加数据迁移、不重建 B 站基线，也不清空队列或冷却。替换前仍须暂停并等待旧代次写入交接，备份代码和数据。0.3.1 候选版尚未替换本次实测的 0.3.0。

## 0.2 → 0.3 升级

1. 先关闭 B 站私信提醒，结束扫码和正在进行的检查，等待旧代次投递、状态与调度写入交接。停止宿主后备份更容易取得一致快照。
2. 备份完整 `0.2.0` 插件代码和整个插件数据目录。数据备份至少包含共享凭据、引擎设置、`bili-dm-state.json` 及宿主保存的插件配置；备份属于用户私密数据，不放进市场包。
3. 原 B 站开关、账号、主人绑定、群目标、历史基线、游标及投递记录继续沿用。不得删除队列来解决升级问题，不改写既有投递键，不把 `pending`／`unknown` 改成待重试。
4. 轮询默认改为 300 秒，可设 180–3600 秒。原值低于 180 秒时一次性迁移为 300 秒，原 180–1800 秒有效值保留。配置成功持久化后才提交迁移完成标记；失败时保留磁盘原配置，内存采用安全间隔并显示迁移待完成。
5. 新增 `private-message-request-state.json` 保存限速窗口、账号命名空间、冷却和恢复元数据。该文件不保存 Cookie 或私信正文。读取损坏、未知版本或写入失败时安全暂停请求，保留原文件供核对。
6. 小黑盒默认为关闭，未通过真实私信验证前不能启用。它的私密配置分区为 `privateMessageProviders.xiaoheihe`，不进入 Python 有效配置，不继承 B 站群目标；本次不凭参考路径创建真实私信账号库。
7. 完成升级后先检查本地状态、迁移说明和接收目标，再按用户授权做低频实测。前端切换平台或折叠区块不改变后台启停状态。

## 0.3 → 0.2 回退

先暂停同步，等待写入交接，备份当前代码与全部数据，再恢复 `0.2.0` 代码。保留新增调度文件和未来小黑盒文件；旧版本不认识这些文件并不代表可以删除。

**0.2 不执行 0.3 的请求协调器。若仍在冷却，回退后须保持提醒关闭，直至冷却结束；不能通过回退绕过服务端等待。** 再次升级时恢复原冷却期限、B 站游标、队列与待核对结果，不重建历史基线或补发不确定消息。

下文保留 0.2 数据结构与更早版本的迁移记录。其中 `0.1.0` 回退步骤属于历史说明，不是本次推荐回退目标。

## Schema

- `bili-dm-state.json`：`schemaVersion: 1`，按机器人实例（`robotKey`）和 B 站 UID 分区。
- 根节点新增有界的 `syncCycles` 调度元数据，按机器人与实际凭据的摘要分区，最多保留 8 项。每项只保存同步周期身份和创建时间；分页未完成和重载沿用同一周期，完整同步成功后更换。该字段不改变原账号游标、消息、队列或投递键，回退时保留。
- 每个账号包含发现进度、会话游标/续拉任务、消息记录和不可变投递分段。
- 绑定目标与 `bindingVersion` 独立于账号；`binding.target` 始终是主人目标，`notifyKind`（默认 `c2c`）和 `groupTarget`/`groupName` 记录可选的唯一自动通知群。发送限速记录也持久化在该文件，重载后继续生效。
- 任何主人或接收目标变更都会增加 `binding.version`；旧版本下尚未尝试的批次保持冻结，不自动改发到新目标。
- 测试及状态通知保存在有界的 `notifications` 集合中，使用持久化序号和独立投递记录；待核对或未知记录不能为腾出容量而删除。
- 明确尚未发送且已撤回的原记录可以进入 `suppressed` 终态，保留核对期并排除待发容量；已进入不确定发送的记录仍保留账本核对状态，不能伪标发送成功。
- `credentials.json` 仍保存共享 B 站 Cookie；`engine-settings.json` 只保存高级引擎配置。

## 升级前

1. 暂停 B 站私信提醒（`/解析 私信 关` 或管理页关闭），等待正在进行的检查、扫码和投递动作结束。
2. 在宿主停止或安全空闲时复制整个插件数据目录，包括 `credentials.json`、`engine-settings.json` 和已有的 `bili-dm-state.json`。保留一份 `0.1.0` 插件代码与数据备份。
3. 确认备份包含当前 `bili-dm-state.json`；不要用媒体缓存清理规则删除它。
4. 若旧版本曾使用 `upstream.bilibili_enhanced.cookie`，新版本会在首次加载时把它归一化到根 `bilibili_enhanced.cookie`，并保留其他平台凭据和无关字段。显式空值视为清除。
5. 旧 Python 运行时鉴权文件不作为本插件 Node 侧登录入口；如发现旧运行时 Cookie 抢占共享凭据，应通过现有 service 适配层处理，不要建立第二个写入者。
6. 新代次在加载设置和私信状态前等待旧代次存储写入尾部；不要在旧进程仍写状态文件时复制或启动第二个实例。

## 回退

1. 先暂停私信并停止旧代次轮询/扫码。不要把仍在 `sending`、`pending` 或 `unknown` 的分段改写成可重试。
2. 备份当前插件代码和数据；回退到 `0.1.0` 代码时**保留 `bili-dm-state.json`**，不要把它当媒体缓存删除。旧代码不会读取它，但再次升级时需要恢复。
3. 保留 `credentials.json` 中的共享 B 站 Cookie，或按用户明确要求单独清除；不要在不了解影响时删除其他平台凭据。
4. 回退后核对原媒体解析可用。私信功能在旧版本中不可用，属于预期。
5. 再次升级到 `0.2.0` 时，已有的 `bili-dm-state.json` 会按原 UID 恢复进度。不得自动重发已冻结、已确认、`pending` 或 `unknown` 的内容；只允许通过宿主账本核对或主人显式「领取」明确未发送的内容。
6. 若升级前已有主人绑定，新增的 `notifyKind` 缺省按 `c2c` 处理；群目标为空时不会自动选择任何群。切换群或切回主人私聊只影响之后新进入的批次，不改变既有冻结、待核对或未知结果。

## 故障处理

- 状态文件损坏或版本高于当前插件：保留原文件并显示安全错误，不重置为空状态、不推进游标、不开始新投递。
- 状态写入失败：内存游标和已发布状态不前进，不开始新发送。
- 从旧高级配置迁出登录信息时，先保存凭据再清理旧来源；写盘失败会保留旧来源，不清空唯一登录值。
- 达到 1000 条未完成消息或 20 MiB 文件上限：暂停抓取，保留现有数据和续拉点。
- 登录失效或网络退避：保留凭据、绑定和队列，只停止读取并在状态中显示原因；只有显式退出登录才清除共享 Cookie。
